# Source Data: Shows and Tickets

## Overview

FANalyze v2.0 processes two distinct data sources that feed into separate but complementary pipelines:

1. **Show Data (Batch)**: Historical and future concert information from SetlistFM API
2. **Ticket Sales Data (Streaming)**: Synthetic real-time ticket sales events

---

## 1. Show Data: SetlistFM API

### Data Source

**API**: [Setlist.fm REST API](https://api.setlist.fm/docs/1.0/index.html)

**Purpose**: Collect historical and future concert/show data for artists

**Collection Method**: Python scripts fetch show data via REST API calls

### Data Collection Process

#### Script: `scripts/export_setlistfm_history_to_csv.py`

**Functionality**:
- Fetches setlists (shows) for configured artists using SetlistFM API
- Extracts show metadata: dates, venues, locations, artist information
- Exports to CSV format for batch processing
- Optionally enriches data with synthetic ticket metrics

**Key Components**:

1. **SetlistFMAPI Class** (`scripts/data_collection/setlistfm_api.py`)
   - Handles API authentication and rate limiting
   - Implements retry logic for API requests
   - Paginates through artist setlists

2. **Data Extraction**:
   - Fetches shows by artist MusicBrainz ID (MBID)
   - Retrieves paginated results (up to 25 shows per page)
   - Filters shows by date range or fetches most recent N shows

3. **CSV Export**:
   - Writes to `data/raw/csv/shows_history.csv`
   - Includes fields: `ARTIST_ID`, `ARTIST_NAME`, `SHOW_ID`, `SHOW_DATE`, `VENUE_NAME`, `VENUE_ID`, `CITY_NAME`, `STATE_CODE`, `COUNTRY_NAME`

### Data Structure

**Historical Shows** (`shows_history.csv`):
- **Source**: SetlistFM API - past concerts with setlist data
- **Key Fields**:
  - `ARTIST_ID`: MusicBrainz ID (MBID) for the artist
  - `ARTIST_NAME`: Name of the performing artist
  - `SHOW_ID`: Unique setlist ID from SetlistFM
  - `SHOW_DATE`: Date of the show (DD-MM-YYYY format)
  - `VENUE_NAME`: Name of the venue
  - `VENUE_ID`: SetlistFM venue ID (may be empty)
  - `CITY_NAME`: City where show took place
  - `STATE_CODE`: State/province code (may be empty for non-US shows)
  - `COUNTRY_NAME`: Country name
  - `SOURCE`: Always "setlist.fm"
- **Enrichment**: May include synthetic ticket metrics (tickets_sold, revenue, attendance_rate) if `--enrich` flag is used

**Future Shows** (`shows_future.csv`):
- **Source**: SetlistFM API - upcoming concert announcements
- **Key Fields**: Similar to historical shows, but focused on future dates
- **Use Case**: Used for ticket sales simulation and forward-looking analytics

### API Configuration

**Authentication**:
- Requires SetlistFM API key
- Configured via environment variables or config file
- API key stored in `config/api_config.py`

**Rate Limiting**:
- SetlistFM API has rate limits (typically 10 requests per 10 seconds)
- Script implements retry logic with exponential backoff
- Respects API rate limits to avoid throttling

**API Endpoints Used**:
- `GET /rest/1.0/artist/{mbid}/setlists` - Fetch setlists for an artist
- `GET /rest/1.0/setlist/{setlistId}` - Fetch detailed setlist information

### Data Flow

```
SetlistFM API
    ↓
Python Script (export_setlistfm_history_to_csv.py)
    ↓
CSV Files (shows_history.csv, shows_future.csv)
    ↓
Airflow Batch Pipeline (ingest_csv_shows__snowflake.py)
    ↓
Snowflake FAN_RAW.shows_his / FAN_RAW.shows_future
    ↓
dbt Batch Pipeline (staging → intermediate → marts)
```

### Collection Modes

1. **Date-Based Filtering** (Default):
   - Fetches all shows since a specified date (`--since`)
   - Useful for historical data collection
   - Example: `--since 2020-01-01`

2. **Batch Mode** (`--batch`):
   - Fetches N most recent shows per artist (default: 100)
   - Useful for initial data load or updates
   - Example: `--batch --max-shows 100`

## 2. Ticket Sales Data: Synthetic Generation

### Data Source

**Type**: Synthetically generated ticket sales events

**Purpose**: Simulate real-time ticket sales for shows to enable streaming pipeline demonstration

**Generation Method**: Python scripts generate realistic ticket sales events based on business logic

### Data Generation Process

#### Script: `kafka/producers/ticket_producer.py`

**Functionality**:
- Generates realistic ticket sales events for upcoming shows
- Publishes events to Kafka topic `ticket_sales`
- Uses business logic to simulate sales velocity and patterns

**Key Components**:

1. **TicketProducer Class**:
   - Extends `BaseProducer` for Kafka integration
   - Generates sale events based on show characteristics
   - Tracks active sales per show to maintain state

2. **Sales Velocity Calculation**:
   - **Artist Tier Multiplier**: A-list artists sell faster than B-list
   - **Venue Capacity**: Larger venues have different sales patterns
   - **Time-Based Multiplier**: Sales accelerate as show date approaches
   - **Weekend Multiplier**: Weekend shows sell faster
   - **Formula**: `base_rate × artist_multiplier × venue_multiplier × time_multiplier × weekend_multiplier`

3. **Event Generation Logic**:
   - Calculates probability of sale based on sales velocity
   - Generates realistic ticket quantities (1-10 tickets per event)
   - Calculates revenue based on ticket price and quantity
   - Tracks cumulative sales per show

### Data Structure

**Ticket Sales Events** (Kafka messages):

**Key Fields**:
- `id`: Unique event identifier
- `timestamp`: Event timestamp (ISO format)
- `show_id`: Reference to show from shows_future
- `artist_name`: Name of the performing artist (used as Kafka partition key)
- `venue_name`: Name of the venue
- `show_date`: Date of the show
- `city_name`: City where show will take place
- `state_code`: State/province code
- `tickets_sold`: Number of tickets sold in this event (1-10)
- `cumulative_tickets_sold`: Running total for this show
- `revenue`: Revenue from this event
- `cumulative_revenue`: Running total revenue for this show
- `venue_capacity`: Total capacity of the venue
- `sales_rate`: Percentage of capacity sold (cumulative_tickets_sold / venue_capacity × 100)
- `days_until_show`: Days remaining until show date
- `artist_tier`: Artist tier classification (A-list, B-list, etc.)
- `average_ticket_price`: Average price per ticket
- `venue_utilization_pct`: Current utilization percentage
- `sales_velocity_per_day`: Calculated sales velocity metric

### Business Logic

**Sales Velocity Factors**:

1. **Artist Tier**:
   - A-list: 1.5x base rate
   - B-list: 1.0x base rate
   - C-list: 0.7x base rate

2. **Venue Size**:
   - Large (>20,000): 0.8x multiplier
   - Medium (5,000-20,000): 1.0x multiplier
   - Small (<5,000): 1.2x multiplier

3. **Time Until Show**:
   - >365 days: 0.1x multiplier (very slow)
   - >180 days: 0.3x multiplier
   - >90 days: 0.6x multiplier
   - >30 days: 1.0x multiplier (normal)
   - >7 days: 1.5x multiplier (accelerating)
   - ≤7 days: 2.0x multiplier (last-minute rush)

4. **Weekend Effect**:
   - Weekend shows: 1.2x multiplier
   - Weekday shows: 1.0x multiplier

**Sale Probability**:
- Based on sales velocity and time since last sale
- Capped at 80% probability per check interval
- Higher velocity = more frequent sales

**Ticket Quantities**:
- Random between 1-10 tickets per event
- Larger quantities more likely for high-demand shows
- Respects venue capacity limits

### Data Flow

```
Snowflake (shows_future data)
    ↓
TicketProducer (reads show data)
    ↓
Generates Sale Events (business logic)
    ↓
Kafka Topic: ticket_sales
    ↓
PostgreSQL Consumer (kafka/consumers/postgres_consumer.py)
    ↓
PostgreSQL staging.ticket_sales table
    ↓
Airflow Streaming Pipeline (sync_streaming_tickets__postgres_to_snowflake.py)
    ↓
Snowflake FAN_RAW.raw_tickets
    ↓
dbt Streaming Pipeline (staging → intermediate → marts)
```

### Generation Characteristics

**Real-Time Simulation**:
- Events generated continuously (every few seconds)
- Simulates real-world ticket sales patterns
- Maintains state per show (cumulative sales)

**Realistic Patterns**:
- Sales accelerate as show date approaches
- High-demand artists sell faster
- Weekend shows have higher velocity
- Large venues have different patterns than small venues

**State Management**:
- Tracks active sales per show
- Maintains cumulative totals
- Stops generating when venue is sold out
- Skips shows that have already occurred

## Data Source Comparison

| Aspect | Show Data (Batch) | Ticket Sales Data (Streaming) |
|--------|------------------|------------------------------|
| **Source** | SetlistFM API | Synthetically generated |
| **Update Frequency** | Weekly batch loads | Continuous (every few seconds) |
| **Data Volume** | 500+ shows per batch | 100+ events per minute |
| **Pipeline Type** | Batch | Streaming |
| **Storage Format** | CSV → Snowflake | Kafka → PostgreSQL → Snowflake |
| **Use Case** | Historical analysis, show catalog | Real-time sales monitoring, demand analysis |
| **Data Freshness** | Weekly updates | Near real-time |

---

## Integration Points

### Show Data → Ticket Data

**Connection**:
- Ticket sales events reference `show_id` from shows data
- TicketProducer reads from `stg_shows_future` to get show information
- Enables realistic ticket sales simulation based on actual show data

**Data Enrichment**:
- Show data provides: artist_name, venue_name, show_date, venue_capacity
- Ticket generation adds: sales events, revenue, sales velocity metrics

### Combined Analytics

**Unified Analysis**:
- Show data provides the catalog of concerts
- Ticket data provides sales performance metrics
- Together enable comprehensive concert analytics:
  - Artist performance analysis
  - Venue utilization trends
  - Demand forecasting
  - Revenue optimization
