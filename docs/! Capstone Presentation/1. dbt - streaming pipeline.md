# dbt Streaming Pipeline Workflow

## Overview
**Data Flow**: Kafka → PostgreSQL → Snowflake `FAN_RAW.raw_tickets` → dbt Transformations → Analytics-Ready Tables

**Pipeline**: Real-time ticket sales events stream through Kafka, land in PostgreSQL staging, sync to Snowflake raw layer, then transform through dbt's three-layer architecture.

---

## Data Source: `FAN_RAW.raw_tickets`

**Source**: Streaming ticket sales data synced from PostgreSQL `staging.ticket_sales` table

**Key Fields**:
- `id`, `timestamp`, `show_id`
- `artist_name`, `venue_name`, `show_date`
- `tickets_sold`, `revenue`, `venue_capacity`
- `sales_rate`, `days_until_show`, `artist_tier`
- `created_at`, `synced_at`

**Sync Process**: Airflow script (`sync_streaming_tickets__postgres_to_snowflake.py`) incrementally syncs new records every 15 minutes.

---

## Layer 1: Staging (`stg_ticket_sales`)

**Materialization**: `table` (materialized as a physical table, not a view)

**Why Table Instead of View?**
- The intermediate layer (`int_ticket_sales_dedup`) queries the staging layer frequently for deduplication
- If staging were a `view`, it would need to **reconstruct the entire result set** every time the intermediate layer queries it
- By materializing as a `table`, the cleaned and validated data is **pre-computed and stored**, so subsequent queries just read from disk
- This reduces compute costs significantly when the intermediate layer performs its window function deduplication logic
- **Trade-off**: Slightly slower initial build, but much faster for downstream queries

**Purpose**: Clean, standardize, and validate raw ticket sales data

### Key Transformations:

1. **Data Quality Checks**
   - Negative values → `NULL` (tickets_sold, revenue, venue_capacity)
   - Invalid capacity (≤0) → `NULL`
   - Filters out records with missing required fields (show_id, artist_name, venue_name, show_date, timestamp)

2. **Key Generation**
   - Uses custom macro: `generate_ticket_sales_key(show_id, timestamp)`
   - Creates unique MD5 hash: `MD5(CONCAT(show_id, '|', timestamp))`
   - Ensures uniqueness for incremental processing

3. **Calculated Fields**
   - **Venue Utilization %**: `(cumulative_tickets_sold / venue_capacity) * 100`
   - **Sales Velocity**: Uses custom macro `calculate_sales_velocity(tickets_sold, days_until_show)`
     - Formula: `tickets_sold / days_until_show` (tickets per day)

4. **Data Standardization**
   - Consistent naming conventions
   - Proper data types
   - Cleaned field names (tickets_sold_clean → tickets_sold)

**Tests**: 
- Uniqueness: `ticket_sales_key`
- Not null: Required fields (show_id, artist_name, venue_name, tickets_sold, revenue)
- Range validation: tickets_sold (0-100), revenue (≥0), venue_capacity (≥1), sales_rate (0-100%)

## Layer 2: Intermediate (`int_ticket_sales_dedup`)

**Materialization**: `table` (for performance on deduplication logic)

**Purpose**: Handle late-arriving data and deduplication

### Key Logic:

**Deduplication Strategy Using Window Functions**:

**What is a Window Function?**
- A window function performs calculations across a set of rows related to the current row
- Unlike aggregate functions (SUM, COUNT), window functions **don't collapse rows** - they add a calculated column
- They use `OVER()` clause to define the "window" of rows to consider

**How This Window Function Works**:
```sql
ROW_NUMBER() OVER (
    PARTITION BY ticket_sales_key
    ORDER BY timestamp DESC, created_at DESC, id DESC
) AS rn
WHERE rn = 1
```

**Step-by-Step Explanation**:

1. **`PARTITION BY ticket_sales_key`**: 
   - Groups rows into separate windows based on the `ticket_sales_key`
   - Each unique key gets its own window
   - Example: If you have 3 records with the same `ticket_sales_key`, they're all in one window

2. **`ORDER BY timestamp DESC, created_at DESC, id DESC`**:
   - Within each window, orders rows by timestamp (newest first), then created_at, then id
   - DESC means descending order (newest = 1, oldest = last)

3. **`ROW_NUMBER()`**:
   - Assigns a sequential number (1, 2, 3...) to each row within its window
   - Row #1 = most recent record (based on ordering)
   - Row #2, #3, etc. = older duplicates

4. **`WHERE rn = 1`**:
   - Filters to keep only rows where `rn = 1`
   - This keeps the **most recent** record for each `ticket_sales_key`
   - All duplicates are eliminated

**Example**:
```
Before deduplication:
ticket_sales_key | timestamp           | tickets_sold | rn
-----------------|---------------------|--------------|----
abc123          | 2024-01-15 10:00   | 50          | 1  ← Kept
abc123          | 2024-01-15 09:00   | 45          | 2  ← Removed
abc123          | 2024-01-15 08:00   | 40          | 3  ← Removed

After: Only the row with rn=1 remains
```

**Why This Matters**:
- Streaming data can arrive out of order or be duplicated
- Same event (`ticket_sales_key`) might appear multiple times
- Keeps **latest** record based on timestamp, then created_at, then id
- Ensures data integrity for incremental fact table

**Output**: One record per `ticket_sales_key` (the most recent version)

**Tests**:
- Uniqueness: `ticket_sales_key`
- Not null: Key fields (ticket_sales_key, timestamp, tickets_sold, revenue)

## Layer 3: Marts (`fact_ticket_sales`)

**Materialization**: `incremental` with `merge` strategy ⭐ **KEY FEATURE**

**Purpose**: Final analytics-ready fact table with business logic and incremental loading

### Incremental Loading Strategy:

**First Run**:
- Processes all records from `int_ticket_sales_dedup`
- Creates initial fact table

**Subsequent Runs**:
```sql
{% if is_incremental() %}
    WHERE ts.timestamp >= COALESCE(
        (SELECT MAX(fact.timestamp) FROM {{ this }} AS fact),
        '1970-01-01'::timestamp
    )
{% endif %}
```
- Queries max timestamp from existing fact table
- Only processes records with timestamp >= max timestamp
- **Impact**: Processes seconds/minutes of new data instead of full table

**Merge Strategy** (How Incremental Updates Work):

The merge strategy uses SQL's `MERGE` statement to intelligently update or insert records:

**Configuration**:
- `unique_key`: `ticket_sales_key` (the identifier used to match records)
- `incremental_strategy`: `merge` (uses MERGE statement instead of DELETE + INSERT)

**How It Works**:

1. **dbt identifies new records**:
   - Queries `int_ticket_sales_dedup` for records with `timestamp >= max(timestamp)` from existing fact table
   - These are the "source" records to process

2. **dbt executes MERGE statement**:
   ```sql
   MERGE INTO fact_ticket_sales AS target
   USING new_records AS source
   ON target.ticket_sales_key = source.ticket_sales_key
   ```

3. **WHEN MATCHED** (record already exists):
   - The `ticket_sales_key` already exists in the fact table
   - **Updates** the existing record with new values from source
   - **Why this matters**: Handles late-arriving data or corrections
   - Example: If a ticket sale event arrives with updated revenue, it updates the existing record

4. **WHEN NOT MATCHED** (new record):
   - The `ticket_sales_key` doesn't exist in the fact table
   - **Inserts** the new record
   - Example: A completely new ticket sale event gets added

**Benefits**:
- **Prevents duplicates**: Even if the same event is processed multiple times, merge ensures only one record exists
- **Handles updates**: Late-arriving corrections or updates are applied automatically
- **Efficient**: Only processes new/changed records, not the entire table
- **Idempotent**: Running the same incremental load multiple times produces the same result

**Example Scenario**:
```
Existing fact table has:
- ticket_sales_key: "abc123", timestamp: 10:00, revenue: $1000

New records to process:
- ticket_sales_key: "abc123", timestamp: 10:00, revenue: $1200  ← MATCHED: Updates revenue
- ticket_sales_key: "xyz789", timestamp: 10:05, revenue: $500   ← NOT MATCHED: Inserts new record

Result: 
- "abc123" updated to $1200
- "xyz789" inserted as new record
```

### Business Logic Added:

1. **Demand Categorization**:
   - `sales_rate >= 80` → 'High Demand'
   - `sales_rate >= 50` → 'Medium Demand'
   - `sales_rate >= 20` → 'Low Demand'
   - `sales_rate < 20` → 'Very Low Demand'

2. **Time-to-Show Categories**:
   - `days_until_show <= 7` → 'Last Week'
   - `days_until_show <= 30` → 'Last Month'
   - `days_until_show <= 90` → 'Last Quarter'
   - `days_until_show > 90` → 'Future'

3. **Revenue Per Ticket**:
   - `revenue / tickets_sold` (when tickets_sold > 0)

4. **Metadata**:
   - `dbt_updated_at`: Current timestamp (always updated)
   - `dbt_created_at`: Current timestamp (for new records)

### Performance Impact:

- **Processing Time**: Minutes → Seconds (90%+ reduction)
- **Compute Costs**: 90%+ reduction vs full refresh
- **Data Freshness**: Analytics available within minutes of event
- **Scalability**: Handles 100+ events/minute efficiently

**Tests**: Comprehensive tests via `schema.yml` ensuring data quality

## Summary: Three-Layer Architecture Benefits

|    Layer    | Purpose |  Materialization | Key Feature |
|-------------|---------|------------------|-------------|
| **Staging** | Clean & validate | `table` | Data quality checks, custom macros |
| **Intermediate** | Deduplicate | `table` | Window functions for late-arriving data |
| **Marts**   | Analytics-ready  | `incremental` | Merge strategy, business logic |

**Key Achievement**: Production-ready incremental loading that processes only new data, reducing costs by 90%+ while maintaining data quality and handling real-time streaming data efficiently.

## Custom Macros Used

**What are dbt Macros?**
- Reusable SQL snippets that can be called like functions
- Defined once, used across multiple models
- Support adapter-specific logic (different SQL for Snowflake vs PostgreSQL)
- Enable DRY (Don't Repeat Yourself) principle

### 1. **`generate_ticket_sales_key(show_id_column, timestamp_column)`**

**Purpose**: Creates a unique identifier for each ticket sales event

**How It's Used**:
```sql
-- In stg_ticket_sales.sql:
{{ generate_ticket_sales_key('show_id', 'timestamp') }} AS ticket_sales_key
```

**What It Does**:
- Takes two column names as parameters (`show_id` and `timestamp`)
- Concatenates them with a pipe separator: `show_id | timestamp`
- Generates MD5 hash: `MD5(CONCAT(show_id, '|', timestamp))`
- Produces a consistent, unique key like: `a1b2c3d4e5f6...`

**Why This Matters**:
- Ensures the same event always gets the same key (idempotent)
- Used as `unique_key` in incremental merge strategy
- Enables deduplication in intermediate layer
- Consistent across all models that need to reference ticket sales

**Example**:
```
Input:  show_id = "show_123", timestamp = "2024-01-15 10:00:00"
Output: "f8a9b2c3d4e5f6a7b8c9d0e1f2a3b4c5" (MD5 hash)
```

### 2. **`calculate_sales_velocity(tickets_sold_column, days_until_show_column)`**

**Purpose**: Calculates how many tickets are sold per day until the show

**How It's Used**:
```sql
-- In stg_ticket_sales.sql:
{{ calculate_sales_velocity('tickets_sold_clean', 'days_until_show') }} AS sales_velocity_per_day
```

**What It Does**:
- Takes tickets sold and days until show as parameters
- Calculates: `tickets_sold / days_until_show`
- Handles edge cases: Returns `NULL` if `days_until_show <= 0` (prevents division by zero)
- Rounds to 2 decimal places

**Why This Matters**:
- Business metric: Shows sales momentum (higher = selling faster)
- Reusable logic: Same calculation used consistently across models
- Safe: Handles edge cases (show already happened, invalid dates)

**Example**:
```
Input:  tickets_sold = 500, days_until_show = 30
Output: 16.67 (tickets per day)

Input:  tickets_sold = 100, days_until_show = 0
Output: NULL (safe handling of edge case)
```

**Benefits of Using Macros**:
- **Consistency**: Same logic applied everywhere
- **Maintainability**: Change once, updates everywhere
- **Readability**: Model code is cleaner and easier to understand
- **Adapter Support**: Can have different implementations for different databases (though we use same logic for both)

## Integration with Airflow

**DAG**: `pipeline_streaming`
- Task 1: Validate Kafka consumer (check PostgreSQL for recent data)
- Task 2: Sync PostgreSQL → Snowflake (`sync_streaming_tickets__postgres_to_snowflake.py`)
- Task 3: `dbt run` (transforms raw → staging → intermediate → marts)
- Task 4: `dbt test` (validates data quality)

**Schedule**: Every 15 minutes (real-time data processing)
