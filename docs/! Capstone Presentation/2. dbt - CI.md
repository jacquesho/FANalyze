# dbt CI Pipeline Overview

> **Note**: This document is part of the Capstone Presentation materials located in `docs/! Capstone Presentation/`

## What is CI?

**Continuous Integration (CI)**: Automated quality checks that run when code is pushed or pull requests are created. Catches issues early before they reach production.

**Why It Matters**:
- **Early Problem Detection**: Issues caught before merge
- **Code Quality**: Ensures consistent formatting and style
- **Data Quality**: Validates transformations work correctly
- **Confidence**: Know code works before deploying

---

## CI Workflow Overview

**Trigger**: Runs automatically on:
- Push to `main` or `develop` branches
- Pull requests to `main` or `develop`
- Only runs dbt checks when dbt-related files change (smart filtering)

**Two Main Jobs**:

### 1. **Code Linting** (Always Runs)
- **Tool**: Ruff (Python linter)
- **Purpose**: Checks Python code quality and formatting
- **What It Validates**: Code style, unused imports, syntax errors
- **Output**: 
  - ✅ **All checks passed!** - No issues found (runs quickly)
  - ❌ **Detailed errors** - Shows file paths, line numbers, error codes, and descriptions if violations found

### 2. **dbt CI - SQL Linting and Testing** (Runs Only on dbt Changes)
- **Smart Filtering**: Only runs if dbt files, SQL files, or CI scripts changed
- **Purpose**: Validates SQL code quality and data transformations

---

## dbt CI Process Steps

### **Step 1: Setup & Validation**
1. **Cache Dependencies**: Restores cached Python packages (faster runs)
   - Uses GitHub Actions cache to avoid reinstalling dependencies
   - Cache key based on `pyproject.toml` hash
   - Speeds up CI runs significantly (seconds vs minutes)
2. **Install Dependencies**: Installs dbt, SQLFluff, and required packages
   - Uses `pr_ci` dependency group (minimal set for CI)
   - Only installs what's needed for testing
3. **dbt Debug**: Validates Snowflake connection and configuration
   - ✅ **Pass**: Connection successful, configuration valid
   - ❌ **Fail**: Connection issue or misconfiguration
   - Runs early to catch connection problems before database setup

### **Step 2: Code Quality Checks**
4. **SQLFluff Lint**: Checks SQL code formatting and style
   - ✅ **Pass**: All SQL follows style guidelines
   - ❌ **Fail**: SQL formatting issues (indentation, spacing, datatype capitalization, etc.)
   - Uses `.sqlfluffignore` to exclude `dbt_packages/` (third-party dependencies)
   - Configured to allow uppercase datatypes (Snowflake style) via excluded rules

### **Step 3: Database Setup**
5. **Create CI Database**: Creates temporary `FANALYZE_CI` database in Snowflake
6. **Load CSV Data**: Loads test data into CI database
   - Provides realistic data for testing transformations

### **Step 4: Transformations & Testing**
7. **dbt deps**: Installs dbt package dependencies
8. **dbt build**: Runs all models AND tests
   - **Builds Models**: Executes all SQL transformations (staging → intermediate → marts)
   - **Runs Tests**: Validates data quality (uniqueness, not null, range checks, etc.)
   - ✅ **Pass**: All models build successfully, all tests pass
   - ❌ **Fail**: Model compilation error, SQL error, or test failure

### **Step 5: Cleanup**
9. **Drop CI Database**: Cleans up temporary database (always runs, even on failure)

---

## What Each Check Validates

### **dbt Debug**
- ✅ Snowflake connection works
- ✅ Credentials are valid
- ✅ Database/warehouse/role permissions correct
- ✅ dbt configuration is valid

### **SQLFluff Lint**
- ✅ SQL formatting follows style guide
- ✅ Consistent indentation and spacing
- ✅ Proper SQL syntax
- ✅ No formatting violations
- **Configuration**: 
  - Excludes `dbt_packages/` directory (third-party packages)
  - Allows uppercase datatypes (Snowflake convention)
  - Configured via `.sqlfluffignore` and `.sqlfluff` config file

### **dbt Build**
- ✅ **Model Compilation**: All SQL compiles correctly
- ✅ **Model Execution**: All transformations run successfully
- ✅ **Data Quality Tests**:
  - Uniqueness checks (primary keys)
  - Not null checks (required fields)
  - Range validation (values within expected bounds)
  - Referential integrity (relationships between tables)

## Interpreting Results

### **All Checks Pass** ✅
```
✓ Code Linting: PASSED
✓ dbt Debug: PASSED
✓ SQLFluff Lint: PASSED
✓ dbt Build: PASSED (all models + tests)
```
**Meaning**: Code is ready to merge. All quality checks passed.

### **Check Fails** ❌
**Example Failures**:
- **dbt Debug fails**: Connection issue → Check credentials/permissions
- **SQLFluff fails**: Formatting issue → Fix SQL style
- **dbt Build fails**: 
  - Model error → SQL syntax/logic issue
  - Test fails → Data quality issue (duplicates, nulls, invalid values)

**Action**: Fix the issue, commit, and CI will re-run automatically.

## Key Features

### **Smart Filtering**
- Only runs dbt CI when dbt-related files change
- Saves CI minutes and time
- Focuses testing on what changed

### **Dependency Caching**
- Caches Python packages between runs
- Faster CI execution (seconds vs minutes)
- Reduces GitHub Actions minutes usage

### **Isolated Testing**
- Creates temporary CI database
- Tests don't affect production data
- Clean environment for each run

### **Comprehensive Validation**
- Code quality (formatting, style)
- Connection validation (credentials, permissions)
- Data quality (tests on actual transformations)
- End-to-end pipeline validation

## Configuration Files

- **`.github/workflows/ci.yml`**: GitHub Actions workflow definition
- **`.sqlfluff`**: SQLFluff configuration (dialect, rules, templater settings)
- **`.sqlfluffignore`**: Excludes `dbt_packages/`, `target/`, `logs/` from linting
- **`.dbt/profiles.yml`**: dbt connection profiles (dev and ci targets)
- **`pyproject.toml`**: Python dependencies including `pr_ci` group for CI
