# dbt Batch Pipeline Workflow

## Overview
**Data Flow**: CSV Files → Snowflake `FAN_RAW` → dbt Transformations → Analytics-Ready Tables

**Pipeline**: Historical and future concert data from CSV files are ingested into Snowflake raw layer, then transformed through dbt's three-layer architecture using dimensional modeling.

---

## Data Sources: `FAN_RAW.shows_his` and `FAN_RAW.shows_future`

**Source 1: Historical Shows** (`shows_his`)
- **Format**: CSV file (`shows_history.csv`)
- **Content**: Past concert data with ticket sales, revenue, attendance
- **Key Fields**: `artist_id`, `artist_name`, `venue_id`, `venue_name`, `show_date`, `tickets_sold`, `revenue`, `attendance_rate`, `is_sellout`
- **Volume**: 500+ records per batch load
- **Update Cadence**: Weekly bulk loads

**Source 2: Future Shows** (`shows_future`)
- **Format**: CSV file (`shows_future.csv`)
- **Content**: Upcoming concert announcements
- **Key Fields**: `show_id`, `artist_name`, `venue_id`, `venue_name`, `show_date`, `city_name`, `state_code`
- **Volume**: Varies based on upcoming concerts
- **Update Cadence**: Weekly bulk loads

**Ingestion Process**: Airflow script (`ingest_csv_shows__snowflake.py`) loads CSV files directly into Snowflake `FAN_RAW` schema.

---

## Airflow Orchestration

**DAG**: `pipeline_batch`
**Schedule**: Weekly on Sunday at 2 AM (`0 2 * * 0`)

**Task Flow**:
1. **Clear Snowflake Schemas**: Truncates raw tables, drops dbt-created schemas (clean slate)
2. **Ingest CSV to Snowflake**: Loads `shows_history.csv` and `shows_future.csv` to `FAN_RAW`
3. **dbt Run**: Transforms raw data through staging → intermediate → marts layers
4. **dbt Test**: Validates data quality for batch-specific models

**Key Difference from Streaming**: 
- **Full Refresh**: Clears and reloads all data each run (no incremental loading needed)
- **Weekly Schedule**: Batch data doesn't change frequently, so weekly updates are sufficient

## Layer 1: Staging (`stg_shows_his`, `stg_shows_future`)

**Materialization**: `view` (not `table`)

**Why View Instead of Table?**
- Batch data is loaded fresh each week (full refresh)
- Views are always up-to-date with source data
- No need to materialize since data doesn't change between weekly loads
- Lower storage costs (views don't store data, they query on-demand)
- **Trade-off**: Slightly slower queries, but acceptable for batch processing

**Purpose**: Clean, standardize, and track data quality for raw CSV data

**Data Quality Philosophy**:
- **Preserve all events**: Don't filter out incomplete records (concert events are valuable even if some fields are missing)
- **Track quality**: Use flags and scores to identify data quality issues
- **Handle downstream**: Allow downstream models to decide how to handle incomplete records
- **Enable analysis**: Can analyze data quality trends and completeness rates

### Key Transformations:

**`stg_shows_his` (Historical Shows)**:

1. **Date Parsing**
   - Handles multiple date formats (MM/DD/YYYY, YYYY-MM-DD)
   - Converts to standard DATE format
   - Example: `"01/15/2024"` → `2024-01-15`

2. **Data Type Conversion**
   - CSV columns are `NUMBER(19,0)` → Cast via VARCHAR to avoid precision issues
   - `tickets_sold`, `revenue`, `attendance_rate`, `average_ticket_price` → Proper numeric types
   - `sellout_status` → Boolean (`is_sellout`)

3. **Data Quality Tracking** (Not Filtering)
   - **Keeps all records** - Even incomplete ones (important for concert events)
   - **Data Quality Flags**: Tracks missing fields without filtering
     - `has_missing_date`: Boolean flag if show_date is NULL
     - `has_missing_artist`: Boolean flag if artist_name is NULL
     - `has_missing_venue`: Boolean flag if venue_name is NULL
     - `has_missing_show_id`: Boolean flag if show_id is NULL
   - **Data Quality Status**: Categorizes completeness
     - `'Complete'`: All critical fields present
     - `'Partial'`: Some fields missing
     - `'Incomplete'`: Most fields missing
   - **Completeness Score**: Percentage (0-100%) of critical fields present
   - **Why This Approach**: Concert events are valuable even if incomplete (e.g., show announced but venue TBD)

**`stg_shows_future` (Future Shows)**:

1. **Simpler Structure**
   - Future shows don't have sales data yet
   - Focuses on show metadata: artist, venue, date, location

2. **Date Handling**
   - Standard date casting (future shows use consistent format)

3. **Data Quality Tracking**
   - Same data quality flags as historical shows
   - Tracks completeness without filtering records
   - Future shows often have incomplete data (venue TBD, date TBA, etc.)

**Tests**: 
- Data quality flags: Ensures flags are calculated correctly
- Completeness score: Validates score calculation (0-100%)
- Date validation: Valid date formats (when date is present)

**How Downstream Models Handle Incomplete Records**:

- **NULLs are safe**: SQL functions handle NULLs gracefully
  - `extract(year from show_date)` returns NULL if show_date is NULL (doesn't break)
  - `avg(attendance_rate)` excludes NULLs from calculation
  - `case when venue_capacity > 0 then ...` safely handles NULL capacity

- **Aggregations ignore NULLs**: 
  - `sum(revenue)` only sums non-NULL values
  - `count(distinct artist_name)` excludes NULLs
  - Group by operations work fine with NULLs

- **JOINs handle NULLs**:
  - `left join ... on a.artist_name = f.artist_name` - NULLs don't match (usually desired)
  - Incomplete records can still be joined if they have matching non-NULL fields

- **Filtering options downstream**:
  - Can filter by `data_quality_status = 'Complete'` if needed for specific analyses
  - Can use `completeness_score >= 75` to include only mostly-complete records
  - Can analyze incomplete records separately to understand data quality issues

**Result**: All events are preserved, data quality is tracked, and downstream models can decide how to handle incomplete records based on use case.

## Layer 2: Intermediate (`int_shows`, `int_artists`, `int_venues`)

**Materialization**: `table` (for performance on aggregations)

**Purpose**: Apply business logic, calculate metrics, and prepare for dimensional modeling

### **`int_shows`** (Show Metrics)

**Key Logic**:

1. **Calculated Metrics**:
   - **Calculated Attendance Rate**: `(tickets_sold / venue_capacity) * 100`
   - **Calculated Sellout**: `tickets_sold >= venue_capacity`
   - **Revenue Per Ticket**: `revenue / tickets_sold` (when tickets_sold > 0)

2. **Date Parts for Analysis**:
   - `show_year`, `show_month`, `show_quarter`, `day_of_week`
   - **Season**: Winter (Dec-Feb), Spring (Mar-May), Summer (Jun-Aug), Fall (Sep-Nov)

3. **Data Enrichment**:
   - Adds temporal dimensions for time-based analysis
   - Enables seasonal and quarterly trend analysis

**Output**: One record per show with calculated metrics and date dimensions

### **`int_artists`** (Artist Aggregations)

**Key Logic**:

1. **Historical Performance**:
   - `total_shows`: Count of distinct shows
   - `first_show_date`, `last_show_date`: Date range
   - `avg_attendance_rate`, `avg_ticket_price`: Average metrics
   - `total_revenue`, `total_tickets_sold`: Aggregate totals

2. **Future Shows Integration**:
   - Joins with `stg_shows_future` to get `upcoming_shows` count
   - `has_upcoming_shows`: Boolean flag

**Output**: One record per artist with historical and future show metrics

### **`int_venues`** (Venue Performance)

**Key Logic**:

1. **Venue Aggregations**:
   - `total_shows`: Count of shows at venue
   - `unique_artists`: Count of distinct artists
   - `avg_attendance_rate`, `avg_ticket_price`: Average metrics
   - `total_revenue`, `total_tickets_sold`: Aggregate totals
   - `sellout_count`: Number of sellout shows
   - `sellout_rate`: Percentage of shows that sold out

2. **Future Shows Integration**:
   - Joins with `stg_shows_future` for upcoming shows
   - `upcoming_shows`, `has_upcoming_shows`: Future show indicators

**Output**: One record per venue with performance metrics and future show indicators

**Tests**:
- Uniqueness: Key fields (artist_id, venue_id)
- Not null: Required fields
- Range validation: Percentages (0-100), positive values

## Layer 3: Marts (`fact_shows`, `dim_artists`, `dim_venues`)

**Materialization**: `table` (for analytics performance)

**Purpose**: Final analytics-ready dimensional model (star schema)

### **`fact_shows`** (Fact Table)

**Key Features**:

1. **Unified Historical + Future Shows**:
   - Combines `int_shows` (historical) and `stg_shows_future` (upcoming)
   - Uses `UNION ALL` to combine both sources
   - **Show Status**: `'Historical'` or `'Upcoming'`

2. **Historical Shows** (from `int_shows`):
   - Full metrics: tickets_sold, revenue, attendance_rate, etc.
   - All calculated fields and date dimensions

3. **Upcoming Shows** (from `stg_shows_future`):
   - Basic metadata: artist, venue, date, location
   - Sales metrics are `NULL` (will be populated as data becomes available)
   - Date dimensions calculated from show_date

4. **Business Logic**:
   - **Show Status**: Distinguishes historical vs upcoming
   - **Days From Show**: Calculated for upcoming shows (`show_date - CURRENT_DATE`)
   - **Metadata**: `ingested_at` timestamp for tracking

**Why This Design?**
- Single fact table for all shows (past and future)
- Enables unified queries across time periods
- Future shows can be updated as sales data arrives
- Supports both historical analysis and forward-looking queries

### **`dim_artists`** (Dimension Table)

**Source**: `int_artists`

**Key Attributes**:
- `artist_id` (surrogate key)
- `artist_name` (natural key)
- `artist_tier` (A-list, B-list, etc.)
- Performance metrics: `total_shows`, `total_revenue`, `avg_attendance_rate`
- Date range: `first_show_date`, `last_show_date`
- Future indicators: `upcoming_shows`, `has_upcoming_shows`

**Purpose**: Provides artist context for fact table analysis

### **`dim_venues`** (Dimension Table)

**Source**: `int_venues`

**Key Attributes**:
- `venue_id` (surrogate key)
- `venue_name` (natural key)
- `venue_type` (Stadium, Arena, Theater, etc.)
- `venue_capacity`
- Location: `city_name`, `state_code`, `country_name`, `market_size`
- Performance metrics: `total_shows`, `sellout_rate`, `avg_attendance_rate`
- Future indicators: `upcoming_shows`, `has_upcoming_shows`

**Purpose**: Provides venue context for fact table analysis

**Tests**: Comprehensive tests via `schema.yml` ensuring data quality

## Summary: Three-Layer Architecture Benefits

| Layer | Purpose | Materialization | Key Feature |
|-------|---------|----------------|-------------|
| **Staging** | Clean & track quality | `view` | Data quality flags, completeness scoring, date parsing |
| **Intermediate** | Business logic | `table` | Aggregations, calculated metrics, date dimensions, NULL handling |
| **Marts** | Analytics-ready | `table` | Star schema (fact + dimensions), handles incomplete records |

**Key Achievement**: Production-ready dimensional model that unifies historical and future show data, enabling comprehensive analytics across time periods.

---

## Key Differences: Batch vs Streaming Pipeline

| Aspect | Batch Pipeline | Streaming Pipeline |
|--------|---------------|-------------------|
| **Data Source** | CSV files | Kafka → PostgreSQL → Snowflake |
| **Update Frequency** | Weekly | Every 15 minutes |
| **Staging Materialization** | `view` | `table` |
| **Incremental Loading** | No (full refresh) | Yes (incremental with merge) |
| **Data Volume** | 500+ records per load | 100+ events/minute |
| **Processing Strategy** | Full refresh each run | Only new/changed records |
| **Use Case** | Historical analysis | Real-time monitoring |

**Why Different Approaches?**
- **Batch**: Historical data doesn't change, so full refresh is simpler and acceptable
- **Streaming**: Real-time data changes constantly, so incremental loading is essential for performance

## Business Logic Highlights

### **Date Dimension Creation**
- Extracts year, month, quarter, day of week
- Calculates season (Winter, Spring, Summer, Fall)
- Enables time-based analysis and trend identification

### **Unified Show Status**
- Combines historical and future shows in single fact table
- Enables queries like: "Show me all Taylor Swift shows (past and upcoming)"
- Supports both retrospective and forward-looking analytics

### **Performance Metrics**
- Attendance rates, sellout rates, revenue per ticket
- Aggregated at artist and venue levels
- Enables comparative analysis across artists and venues

### **Future Show Tracking**
- Links upcoming shows to historical performance
- Enables predictive analytics: "Artists with high historical attendance have X upcoming shows"

## Testing Strategy

**Source Tests**: Validate `FAN_RAW.shows_his` and `FAN_RAW.shows_future` structure

**Model Tests** (per layer):
- **Staging**: Data quality flag validation, completeness score validation, date validation (when present)
- **Intermediate**: Uniqueness, range validation, handles NULLs gracefully
- **Marts**: Comprehensive data quality checks, referential integrity, NULL handling for incomplete records

**Automation**: Tests run automatically in Airflow pipeline after `dbt run`
